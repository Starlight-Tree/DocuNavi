# 検索の設計（DB のベクトル検索に一本化した理由と、見直す条件）

チャットの検索（`search_documents`）は、**DB（Supabase / pgvector）の `chunks` へのベクトル検索だけ**です。ローカルの PDF を読む
BM25 の経路と、`SEARCH_BACKEND`・`SEARCH_SCOPE` の切り替えは、なくしました。この文書は、そう決めた根拠と、いつ見直すかを残します。
環境変数と動かし方は [configuration.md](configuration.md)、測定の詳細は [evals/README.md](../evals/README.md) と `evals/search_compare/` です。

## 決めたこと

| 項目 | 決定 |
|---|---|
| 検索 | 質問を `gemini-embedding-2`（768 次元）で埋め込み、`chunks.embedding` とのコサイン類似度が高い上位 2 件（`TOP_K`）。DB の `status = 'ready'` の文書が対象 |
| しきい値 | 類似度 0.65 未満のチャンクは返さない（`app/search_vector.py` の `MIN_SIMILARITY`）。**粗い下限**で、「資料にない」の判断は LLM に任せる |
| 失敗したとき | 別の経路に戻らない（どちらで答えたかが曖昧になるため）。API は 503 の固定文を返す |
| DB と API | 本物の LLM では `DATABASE_URL` と `GEMINI_API_KEY` が必須。揃わなければ起動を失敗させる |
| モックモード | `GEMINI_API_KEY` が未設定。資料の検索も回答もしない固定の返答（画面と API の動作確認用）。DB も API も要らない |
| BM25 | アプリからは外した。評価用の基準線として `scripts/bm25_baseline.py` に残した（アプリは import しない） |
| pgroonga（`0004`） | 拡張と索引は DB に残す。アプリは使わない。撤去は DB の変更なので、必要になったときに別に判断する |

## 根拠

### 検索の方式（最終確認、2026-10-18）

方式を選ぶための質問（68 問）とは別に、**固定した 52 問を 1 回だけ**測った（`evals/search_compare/final.json`。測定後に質問は変えていない）。
質問は 2 組: 別の subagent に書かせた 26 問（`final_questions_independent.yaml`）と、Claude が書いた 26 問（`final_questions_claude.yaml`）。
答えのある 38 問・資料外 14 問。指標は、正解チャンクが上位 k 件に入ったか（hit@k）と、最初の正解の順位の逆数の平均（MRR）。

| 方式 | MRR | hit@1 | hit@3 | hit@5 |
|---|---|---|---|---|
| **ベクトル単独** | **0.925** | **32** | **38** | **38** |
| BM25 + ベクトル（RRF） | 0.858 | 28 | 36 | 38 |
| pgroonga + ベクトル（RRF） | 0.862 | 28 | 37 | 37 |
| BM25 | 0.699 | 22 | 32 | 34 |
| pgroonga | 0.670 | 17 | 33 | 33 |

- 作成者別（subagent の組・Claude の組）でも、選定用の質問に正解チャンクが重ならない 16 問（`new_chunk`）でも、ベクトル単独が最良だった
  （新しいチャンクの MRR: ベクトル 0.958、BM25 0.681）。
- 選定用の質問では、pgroonga + ベクトルが最良に見えていた。**最終確認では再現しなかった**。pgroonga は日本語の順位に同点が多く、RRF で足を引っ張った
  （f002・g011 など）。ハイブリッドが不要という意味ではない（下の「見直す条件」）。

### しきい値 0.65 と、LLM に断らせること

類似度では「資料にある話題の質問」と「資料にない質問」を分けられない。答えのある質問の 1 位は 0.62〜0.89、資料にない話題だが関連する質問は 0.67〜0.78、
無関係な質問は 0.66 以下で、重なる。そこで下限は低めにして、明らかな無関係だけを切り、残りは LLM がプロンプトの指示（「資料に書かれていないことは推測せず、
『資料には記載がありません』と答える」）で断る。

- **回答の評価（実 API、14 問、`evals/results/answers_vector_20261018*.json`）。** 資料にない話題の質問 11 問は全て断った。答えのある 3 問は断りすぎなかった。
  境界例が 1 問（a010）。`temperature` が 1.0 のままなので、1 問 1 回の結果は「傾向」として読む。
- **最終確認の 52 問の 1 位の類似度（read-only で計算。API は呼んでいない）。** 答えのある 38 問は 0.677〜0.856 で、全て 0.65 を超える（断りすぎは出ない）。
  無関係な 4 問は 0.556〜0.613 で、全て 0.65 未満（検索が空になる）。資料にない話題の 10 問は 0.690〜0.785 で、全て 0.65 を超える（LLM が断る側）。
  この 10 問を LLM に通してはいない。

### 上位件数（`TOP_K`）としきい値の現状（2026-10-19、API は呼んでいない）

`python -m scripts.eval_topk`（保存済みの質問の埋め込みと DB の読み取りだけ。結果は `evals/results/topk_probe.json`）で、選定用の質問と最終確認の 52 問を合わせた
120 問（答えのある 84 問）を数えた。**数えただけで、値を選ぶ測定ではない**（最終確認の質問は方式の選定に使い終えている）。

| 上位 K 件 | 根拠が返った（84 問中） | 返ったチャンクのうち根拠を含む割合 |
|---|---|---|
| 1 | 66 | 86% |
| **2（いまの `TOP_K`）** | **75** | **51%** |
| 3 | 78 | 37% |
| 5 | 79 | 26% |

- **2 件目の多くは根拠を含まない。** 2 件返った 75 問のうち、2 件目が根拠を含むのは 10 問だけ（うち 2 問は 1 位も根拠）。1 件にすると 9 問が落ちる（K=1 と K=2 の差）。
  根拠を含まない 2 件目は、LLM には渡るが、1 位との差が `WEAK_GAP`（0.05）を超えれば出典カードには出ない（`app/agents/tools.py`）。
- **K=2 で根拠が返らない 9 問の理由。** 4 問はしきい値 0.65 で切れた（根拠のチャンクは 1 位。類似度 0.615〜0.648。どれもザーハードの短い質問: 「硫化水素」「象形文字」など）。
  5 問は根拠が 3 位以下: ザーハードの 2 ファイルにまたがる質問 2 問（q030・q032）、同じ資料の別のチャンクに負けた 1 問（q017。根拠は 4 位）、カフェ 1 問（g011）、入寮規程の 1 問（f016。別の資料の短いチャンクが上位に来て、根拠は 3 位・類似度 0.633 で、しきい値でも切れる）。
- **しきい値 0.65 は、答えのある質問を 4 問（4.8%）切る。** 0.62 に下げても、資料外の質問が LLM まで通る数は変わらない（36 問中 22 問のまま）。
  0.62 で切れるのは 1 問。**ただし、この 120 問で選んだ値ではない**ので、変えるなら新しい質問を先に固定して測る。
- **切れた 4 問を LLM まで通すと、4 問とも「資料には記載がありません」と断った**（実 API、`/chat` と同じ `ainvoke`、1 問 1 回、LLM 呼び出し計 8 回、
  `evals/results/answers_floor_cut_20261019.json`、質問は `evals/answers/questions_floor_cut.yaml`）。LLM が作った検索クエリは質問の短縮形（「硫化水素」
  「象形文字」「昼と夜の気温差」「メタンガス」）で、4 問とも検索が空になり、「別のキーワードで再検索してください」という返りがあっても、再検索せずに断った。
  資料には答えがあるので、これは取りこぼし。1 問 1 回（`temperature` は 1.0）なので傾向として読む。**直し方は未決定**（しきい値を下げる / 空のときの扱いを変える、など。
  変えるなら、新しい質問を先に固定して測る）。
- **空のときの扱いを変えて（2026-10-19、e8f82c0）、測り、戻した（次の項）。** 検索ツールの空の返答（`_NOT_FOUND_TEXT`）と `SYSTEM_PROMPT` に、「すぐ断らず、言い換え・別の語・より一般的な語・短い文で、
  最大 2 回まで検索し直し、それでも見つからないときに限り断る」を足していた。しきい値・`TOP_K`・ツールの説明は変えていない。**効果が確認できず、呼び出しが増えたので、この文面は元に戻した**（アプリの文面は「別のキーワードで再検索してください」に戻っている）。
- **言い換えの再検索の測定（2026-10-19、実 API、1 問 1 回、`ainvoke`、`temperature` 1.0、ヘッジ・再試行・フォールバックなし、しきい値 0.65）。
  事前に固定した基準 (a)〜(d) を全部は満たさず、「効果が確認できない」。** 質問は `evals/answers/questions_research.yaml`（14 問）と
  `questions_floor_cut.yaml`（前の 4 問）、結果は `evals/results/answers_research_before_2_20261019.json`・`answers_research_current_2_20261019.json`・
  `answers_floor_cut_research_2_20261019.json`（1 回目の 3 ファイルは 429 で失敗した記録。判定に使っていない）。429 は 2 回目では出ていない。
  - (a) 答えのある 10 問で「答えた」: 変更前の文面 10、言い換え再検索の文面 8（n006・n010 は最後の回答の呼び出しが 504 で失敗。失敗として数え、再実行していない）→ **満たさない**。
  - (b) 前の 4 問（言い換え再検索の文面）で「答えた」: 1 問（q008 は 3 回目の検索「有害物質」で当たった。q010・q012 は取りこぼし、q019 は 504 で失敗）→ **満たさない**（2 問以上が条件）。
  - (c) 資料外 4 問の「作り話」: 0 → 満たす。 (d) 呼び出しの上限に当たった質問: 0 → 満たす。
  - 見えたこと（観測であり、文面を直す根拠にはしない）: 検索が空だった前の 4 問では、LLM は実際に 2〜3 回検索し直した。ただし言い換えは短い語どうし（「H2S」「文字の起源」「気温」）で、
    どれも空のままだった（当たったのは q008 の 1 問）。また、1 回目が空でなかった資料外の質問 3 問（n011〜n013）でも、言い換え再検索の文面は検索を 2 回にした（呼び出しが 2 → 3 回）。
  - 限界: 1 問 1 回、少数。504（`GoogleAPIError`）が言い換え再検索の文面の側で 3 問に出た（変更前では 0）。文面の影響かは分からない。
    直すなら、新しい質問を先に固定して測る（ハイブリッド検索、ツールの説明の変更は別の変更として別に測る）。
- **チャンクの大きさ。** 入寮規程は 3 チャンク（465〜805 文字、ページ単位）で、他は 41〜514 文字。入寮規程の質問 13 問は、K=2 で 12 問に根拠が返る（外れた 1 問は f016）。
  この質問数では、チャンクの大きさが原因の取りこぼしは見えていない（長いチャンクで具体的な質問の類似度が下がるかは、質問が足りず判断できない）。

### 小さい資料での結果であること

資料は 6 冊・80 チャンクで、検索が当てやすい規模です。ベクトル単独が最良だったのは、**この規模での結果**で、ハイブリッドやリランカーが不要という証拠ではありません。

## 見直す条件

次のどれかになったら、方式を測り直す。

- 資料が増えて、チャンクが数百を超えた（目安）。
- 言い換えではなく、型番・固有名詞・数値の完全一致が多い資料を足した（語の一致に強い検索が効きやすい）。
- 回答の評価で、検索が原因の取りこぼし（答えのチャンクが上位 2 件に入らない）が目立つようになった。

測り直すもの:

1. **ハイブリッド**: ベクトル + キーワード（BM25 基準線 `scripts/bm25_baseline.py`、または pgroonga。拡張と索引は `0004` で DB に残してある）を RRF で合わせる。
   pgroonga は日本語の順位の同点が多かったので、同点の処理や分かち書きの設定から見直す。
2. **リランカー**: 1 次検索の上位 20〜100 件を、質問との関係を読み直す別のモデル（クロスエンコーダー）で並べ替え、上位だけを LLM に渡す。
   BM25 や pgroonga（1 次検索）とは別の段。精度は上がりうるが、候補の数だけ呼び出しと遅延が増える。いまの規模では足す理由がない。

手順は、`scripts/eval_search_compare.py`（5 経路の比較）と `scripts/eval_vector.py` を使い、**質問を先に固定してから**測る（選定用と最終確認を分ける。
最終確認は 1 回だけ）。実 API（質問の埋め込み）を使うので、送る件数と上限を決めてから実行する。

## 確かめていないこと

- 画面が使う `/chat/stream` を、本物の LLM と DB で通した確認（`/chat` と同じグラフの経路で、測定は `/chat` と同じ `ainvoke`）。
- 質問ごとの遅延と費用: 質問のたびに埋め込みの API を 1 回呼ぶ。評価では 8 件を 1 回で送って 1.1〜1.4 秒（1 件ずつの遅延は測っていない）。
- Vertex AI で LLM を使う場合の本番構成: 質問の埋め込みは API キー（`GEMINI_API_KEY`）で呼ぶ（`vertexai=False` を明示）。Vertex AI の ADC で
  `gemini-embedding-2` を呼ぶ経路は作っていない。デプロイの手順（[deploy.md](deploy.md)）には、`DATABASE_URL` と `GEMINI_API_KEY` の両方が要る。
- 最終確認の質問のうち、subagent の組の独立性は自己申告（14/19 が選定用の正解チャンクと重なる）。Claude の組は、先の結果を知った上で書いた。
- 答えのある質問は 38 問で、1 問が約 2.6 ポイント。
