## 3. docunavi との接続方法

人が間に入る**手動のバッチ**にする。docunavi のサーバーから星庭側のジョブを自動で呼ばない（第 1 版）。

```text
運営者:  python -m app.hero_images plan   → 候補の資料と、組み立てたプロンプトの一覧（plan.json）を出す  ※実 API は呼ばない
利用者:  plan.json を見て承認 → Imagen App 2026 のバケットへ置き、ジョブを実行（gcloud。書き込みなので利用者が実行）
ジョブ:  タスクごとに plan.json の自分の行を読み、画像を作り、同じバケットへ PNG を書く
運営者:  画像を目で見て確かめる → python -m app.hero_images import → DB に「下書き」で入る → 「公開」にして初めて表示される
```

- `plan` と `import` は docunavi 側の運営者用コマンド（`python -m app.ingestion` と同じ並び）。`plan` はプロンプトを組み立てるだけで、外部へは何も送らない。
- 星庭側へ渡すのは、`plan.json`（資料 ID・主題・組み立て済みのプロンプト・枚数の上限）だけ。DB の接続情報も資料の本文も渡さない。
- 後で自動化する（第 2 版）なら、docunavi の実行用サービスアカウントに、そのジョブだけを実行する権限を付ける。**今は不要。**

## 5. 画像の保存先（Storage か DB か）— D2

| 案 | 長所 | 短所 |
|---|---|---|
| **DB（`bytea`、別表）** ← 第 1 版の推奨 | 可視性の判定を既存の SQL と同じにできる。新しいサービス・認証情報が要らない。バックアップに入る | 画像が増えると DB が太る。API が画像を中継する |
| R2（資料の PDF の置き場と同じ系統） | 大きくなっても安い | 書き込み用の鍵が要る。可視性は API の中継が要る |

- 画像 1 枚は数百 KB 以下の見込みで、5〜数十枚なら、合計は数 MB〜数十 MB。第 1 版は DB で足りる。
  **移す条件（案）:** 枚数が 100 を超える、または合計が 50MB を超える、または他の画面（一覧のカードなど）にも出して配信が重くなったとき。
- 表のイメージ（実装は承認の後。ここでは作らない）: `document_images`（資料 ID、生成時の資料の `content_hash`、種類 `hero`、MIME、バイト列、
  幅・高さ、プロンプトのハッシュ、モデル名、状態 `draft` / `approved` / `rejected`、作成・承認の日時）。
- 返し方: `GET /documents/{id}/hero`（`/file` と同じ認可・同じ 404）。`approved` の画像がなければ 404。
  画面は、`fetch` で取得して blob の URL にする（`<img src>` は Authorization ヘッダーを送れないため。`fetch` は `api/` に置く規約どおり）。
  取得に失敗したら灰色の代替表示のまま（9 節）。
- **生成した画像は、人が見て `approved` にするまで出さない。** 文字・顔・ロゴが混じる、不適切、などを止める関所を兼ねる。

## 6. 生成のタイミング

- **第 1 版は、運営者が `plan` を実行したときだけ。** 取り込みの完了や更新を契機に自動では作らない（費用と、確認なしに外部へ送ることを避ける）。
- `plan` の候補は、ヒーローに出る資料（最大 5 件）のうち、①承認済みの画像が無いもの、②運営者が「作り直し」を指定したもの。
- **更新時に作り直すかは、資料ごとに選ぶ。** 既定は作り直さない（題名と主題が変わらない更新で、画像を替える必要は小さい）。
  資料の `content_hash` が、画像を作ったときと変わったものは、`plan` が「更新あり」と表示するだけにして、作り直しは運営者が選ぶ。
- 第 2 版（別に承認）: 取り込みの完了で「画像が要る」印を付けるところまで。実行は、これまでどおり人の承認つきのバッチ。

## 7. プロンプトに入れる情報 — D3

組み立ては固定の型に、次の 2 つを入れるだけ。

| 入れるもの | 出どころ |
|---|---|
| 種別名（例「カフェ」「ガイド」「ザーハード設定」） | 資料グループの表示名（既存の表） |
| **主題（短い語、1〜3 語・20 文字以内）** | 運営者が `plan` で入力する。例「寮の規程」「家電の取扱説明」 |

入れないもの: 資料の本文・要約・ファイル名・資料の題名の生の文字列・更新日・人名。

固定の型（案。承認の対象）:

```text
Abstract, business-style hero illustration for a document about "{主題}" in the "{種別}" category.
Flat geometric shapes and soft gradients, calm teal and navy palette, wide landscape composition,
subject centered with generous empty margins. No text, no letters, no numbers, no logos, no people, no faces.
```

- 「文書ごとに違う雰囲気」は、主題と種別の違いで出す。要約からの自動生成は、除去の仕組みと確認の流れができてから（第 2 版）。
- 縦横比は、1:1 で作って `object-fit: cover` で切る案が最小。枠が約 2.4:1 なので、1:1 の画像は上下が大きく切れる。
  構図を中央に寄せる指示（上の型に入れた）で補う。横長の指定ができるかは D5 の 1 枚で確かめる（できなければ 1:1 のまま）。

## 8. 個人情報・機密情報の除去

資料には、個人の実名や機密が入りうる（この環境の運用でも、資料の個人の実名を文書や返答に入れない方針）。そこで、**除去ではなく「入れない」**を基本にする。

1. **許可リスト方式:** 外へ出る文字列は、固定の型と、種別名と、運営者が書いた短い主題だけ（7 節）。資料の本文は、画像生成の経路に入らない。
2. **機械の検査:** `plan` が、主題とプロンプト全体を検査し、通らなければ plan に載せない。メールアドレス・電話番号・URL・郵便番号・連続する数字・`AIza` 形式の鍵、
   登録語（`scripts/check-sensitive-terms.sh` と同じ語の一覧。Git の管理外）に一致したら止める。
3. **人の確認:** 利用者が、plan.json の**プロンプトの全文**を見て承認する（11 節）。承認しないものは送られない。
4. **出力の確認:** 画像を目で見て、文字・顔・ロゴ・実在の何かに似たものがないか確かめてから `approved` にする。
5. **外へ出る先の性質:** Vertex AI は、顧客のデータで事前の許可なく学習しない（等級 B）。ただし不正利用の検知で記録されうる。`global` は処理地域を固定しない。
   機密を送らない設計なので許容するが、**ここは限界として残る**。
- 参考: docunavi は、チャットで資料の本文を Gemini へ送っている（無料キーは入力が製品改善に使われる扱い。[configuration.md](configuration.md)）。
  画像生成は、それより外へ出す情報を**大幅に減らす**（本文を送らない）設計。

## 9. 失敗したときの代替表示

- **画面:** 承認済みの画像が無い、取得に失敗した、画像の読み込みに失敗した、のどれでも、いまの灰色の代替表示のまま。文字と操作は画像なしで動く（実装済み・単体テスト済み）。
- **生成の失敗**（ジョブの失敗、安全フィルターで画像が返らない、時間切れ）は、資料の取り込みと表示を止めない。生成は取り込みと別の経路のため。
- **再試行は自動にしない。** 失敗した資料は plan に「失敗・未生成」と出し、運営者が選んだときだけ次の承認に載る。1 回の承認の枚数の上限が、再試行の暴走を止める。
- 星庭側ジョブの「画像なしでも終了コード 0」は、失敗を見逃す。12 節の変更で、画像が 0 枚なら失敗の終了コードにする。
