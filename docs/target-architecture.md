# 目標構成

この文書は、将来の構成の方向と、それぞれを採用する条件をまとめたものです。**実装の契約ではありません。** 今動いている構成は [architecture.md](architecture.md)、
段階の順序は [roadmap.md](roadmap.md) にあります。構成の判断は、測定か要件が出たとき、または利用者が学習のために採用すると決めたときに行い、先に終着点として固定しません。

## 目的

ドキュナビは、今の製品を作るだけでなく、**大規模なマルチテナントの AI SaaS に要る構成を、実際に足して動かして学ぶ練習も兼ねる**（利用者の位置づけ、2026-10）。
Go の SSE 中継、Django、gRPC、組織・権限・課金は、いまの製品には要らないが、「いつか足すかもしれない」で終わらせず、将来の終着点として学習と検証の対象にする。

- **今すぐ全部を実装するのではなく**、順番を決めて 1 つずつ足す。足す前に、何を学ぶか、どう測るか、戻し方を決める。
- 学ぶこと: SSE の接続の分離、AI・文書処理の分離、SaaS 管理の分離、サービス間の認証、スキーマの持ち主とマイグレーションの境界、マルチテナントのデータ分離、監視とトレース。
- 学習のために足すときも、本番の挙動と運用の負担は変わる。足す前に、利用者の承認を取る（CLAUDE.md）。

## 開発環境: ローカル Supabase（設計。2026-10-25。中止）

**現状（2026-10-25）:** 中止（利用者の指示）。段階 0 の検証に使ったローカル Supabase（コンテナ、ボリューム、イメージ、ホストの `supabase` CLI）は削除済み。今動いているのは Compose の `db`（ローカルの Postgres）と本番の Supabase で、ローカル Supabase は動いていない。再開するときは `supabase init` と `supabase start` から。

**方向（利用者の指示、2026-10-25）:** 開発環境の DB と Auth を、ローカルの Supabase（Supabase CLI の `supabase start`）にそろえる。本番は Supabase Platform のまま。
**決めていないこと:** Compose の `db` との関係。**「置き換え候補」**であって、置き換えるか併用するかは、この文書のレビューのあとに利用者が決める。

```
ホスト（Mac、OrbStack）: supabase start ── Auth :54321 / Postgres :54322 / Studio :54323（pgroonga 入り）
開発コンテナ・Compose の api ── ホストのポートへ到達（下の「接続の注意」）
本番: Supabase Platform（変えない）
```

**ねらい:** ログインの確認が本番にしかない状態をなくす。ローカルの Auth で、JWT の検証・更新・利用者ごとの分離を、本番に触れずに繰り返し試す（本番の履歴に確認用の会話が残る問題も避ける）。
本番の Postgres には pgroonga があるが、Compose の `db`（`pgvector/pgvector:0.8.7-pg17`）には無い。ローカル Supabase なら両方そろう。

**段階 0 の実測（2026-10-25、証拠等級 A。ホストの作業用フォルダー〔リポジトリの外〕で `supabase init` + `start`。CLI の版は記録していない）:**

- JWKS（`/auth/v1/.well-known/jwks.json`）は鍵 1 本、EC P-256 / ES256、`kid` 付き。アプリの `_parse_keys` が ES256 の鍵として受け付けた。
- ローカルでサインアップして得たトークンのヘッダーは `alg: ES256`、`kid` が JWKS の鍵と一致。つまり、**署名方式の面では、アプリの認証コードの変更は要らない。**
- 拡張: `vector` 0.8.2、`pgroonga` 3.2.5 が使える。Postgres は 17.11。`extensions` スキーマはあり、`chatbot` スキーマはまだ無い。

**未確認（段階 2 以降）:** `chatbot` スキーマとマイグレーション 0001〜0005 の適用、アプリとローカル Auth の接続、E2E、トークンの `iss` の値（`http://127.0.0.1:54321/auth/v1` と推測。未確認）。

**接続の注意（読んで分かったこと。アプリの変更の要否に関わる）:** `app/auth.py` は、`SUPABASE_URL` の `http` を `localhost` とループバックの IP にだけ許し、`iss` が `{SUPABASE_URL}/auth/v1` と一致することを求める。
そのため、開発コンテナや Compose の `api` から `http://host.docker.internal:54321` を `SUPABASE_URL` にする案は、今のままだと拒否される。対策の案は 2 つ。
(a) コンテナの中で `127.0.0.1:54321` をホストへ転送する（アプリの変更なし。転送の仕組みの追加が要る）。(b) アプリ側で、許すホストや JWKS の取得先を分ける（認証コードの変更。ガードを緩めるので慎重に）。どちらにするかは段階 2 で決める。

**注意（デメリット）:**
- 本番との差はゼロにならない（接続用のプーラー、メール送信、Google の OAuth クライアントなど）。**ローカルで通っても本番で通る保証にはならない。** Google ログインの画面を通る部分は、本番での最終確認のまま。
- 設定が 2 か所（ローカルの設定ファイルと、本番のダッシュボード〔Redirect URLs など〕）になり、ずれうる。
- コンテナが約 10 個増える。起動・停止はホストで行う（開発コンテナの中には Docker エンジンが無い）。
- ローカルの DB は空で始まる。資料を入れ直すには、埋め込みの実 API が要る。
- **全サービスが `0.0.0.0` で待ち受け、Studio は認証なし**（CLI の起動時の警告）。外出先・共用の Wi-Fi では `supabase stop` で止める。鍵は既定のローカル用の値で、本番の鍵と取り違えない。

**段階:** 0 = 起動と署名方式・拡張の確認（済み。上）/ 1 = この設計の記録（本節と roadmap の ⑧）/ 2 以降 = マイグレーションの適用、アプリへの接続、Compose の `db` との関係、E2E の移行（それぞれ承認を取る）。

## 測定済みのこと（プローブ。LLM・DB・秘密なし。2026-10-22〜24。証拠等級 A）

- SSE（最初の本文を 60 秒遅らせる）と 5 MB のバイナリは、Worker を通しても順に届く。Cloud Run の 90 秒で切れるまで、Free プランの Worker の制限に当たらなかった。
  Cloudflare の 125 秒（524）は、先に Cloud Run が切るので未測定。
- 切断: Cloud Run の既定（コンテナまで HTTP/1.1。uvicorn）では、クライアントを 3 秒で切っても、コンテナの処理は最後まで走った（4/4。直接も Worker 経由も同じ）。
  `--use-http2`（ポート名 `h2c`）+ hypercorn では、6/6 で伝わった（直接も Worker 経由も）。
- 含意（実アプリでは**未確認**）: 本番の `docunavi` は、停止やタブを閉じたときに LLM 呼び出しを取り消していない可能性がある。
- 測定のコードは測定後に削除した（Git には入れていない）。

## 採用条件

次の条件は、**製品の必要から採用する場合**の基準です。「目的」にあるとおり、**学習のために採用する場合**は、利用者が決めたときに採用できます（上の条件を満たさなくてもよい）。
その場合も、足す前に、学ぶこと・測ること・戻し方を決めて、承認を取ります。

### Go の SSE 中継

次のどれかを満たしたとき。
- 同時の SSE 接続数が、FastAPI の測定した容量を超える。
- SSE の p99 の遅延が、製品の要件になる。
- SSE の接続のせいで、Cloud Run のメモリやインスタンス数が増える。
- AI 処理の失敗が、SSE の可用性に影響し始める。

### gRPC のサーバーストリーミング

Go の SSE 中継を採用し、かつ Go と Python の間でサーバーストリーミングが要るとき。

### Django

次のどれかが実際の要件になったとき。組織、課金・有料プラン、役割ごとの権限、運用の管理画面（Supabase Studio で足りなくなったとき）。

入れるときの前提:
- 認証の窓口は Supabase Auth のまま。Django は JWT の `sub` を外部 ID として扱い、自前のユーザー表・セッション認証は使わない（二重管理になる）。
- 同じ Postgres を共有するときは、スキーマごとにマイグレーションの持ち主を分ける（`chatbot` は今のリポジトリ、新しい `saas` などは Django 側）。

### Celery + Redis（または Pub/Sub）

取り込みや埋め込みが長時間になり、再試行・優先度・並行数の制御が要るか、API と別にスケールさせたいとき。

### LLM ゲートウェイ

複数のプロバイダーを使うか、モデルの振り分け・費用の上限・切り替えが、今の実装（`app/agents/resilience.py`）で足りなくなったとき。

## 段階 7（Vercel）の前に決めること

**決定（2026-10-24、利用者）:**

- API のつなぎ方: 移行の期間は、Vercel から Cloud Run を直接呼ぶ。Worker はドメインの取得後。切り替え時に `CORS_ORIGINS` を Vercel の URL に絞る（**済み**。2026-10-25 に読んだ本番の値は `https://docunavi-eosin.vercel.app` だけ。コードの既定は `*` のまま）。
- Vercel のデプロイ（**2026-10-24 に変更。利用者の指示: 自動化を後回しにしない**）: 最初の 1 回だけ CLI で手動デプロイして URL を確定し（Supabase の Redirect URLs と Cloud Run の `CORS_ORIGINS` に入れるため）、**そのあと続けて Git 連携に移す**。`main` = 本番。Root Directory は `frontend-next`。以前の決定は「Git 連携は止め、手動のデプロイだけ。安定してから見直す」だった。
- プレビューの API と DB: 本番の DB に接続させない。静的な確認か、ローカル・別の DB だけにする。実装は、Vercel の **Preview の環境変数に `NEXT_PUBLIC_API_BASE_URL` を入れない**こと（API を呼べない）と、Cloud Run の `CORS_ORIGINS` にプレビューの URL を入れないこと（入れても弾かれる）。Supabase の別プロジェクトは、Preview でログインまで確かめたくなってから。
- FastAPI の静的配信: **2026-10-24 に外した**（Vite の `frontend/` ごと削除。利用者が Vercel 上の `frontend-next` でログインと質問を確認した後、決定）。退路は git の履歴と、Vite 版のイメージを持つ Cloud Run の以前のリビジョンだけ。API のみのイメージ（`docunavi-00016-ces`）を 2026-10-25 に promote 済みで、本番の Cloud Run の `/` は 404（画面は配信しない）。

**まだ決まっていない・未確認:**

- プレビュー環境の API と DB の分離（Vercel の環境変数だけでは DB を分けられない）。
- Git 連携の後の運用: `main` へのプッシュで Vercel の本番が更新される。CLAUDE.md の「CI の結果の扱い」「プッシュ」の運用を見直す（`ci.yml` に `frontend-next` のジョブ〔単体テスト・型検査・ビルド〕を足した。2026-10-24）。連携は Vercel の GitHub アプリをこのリポジトリに入れる外向きの設定で、利用者が行う。
- Worker が付ける秘密ヘッダーを FastAPI が検査し、`*.run.app` への直接のアクセスを防ぐ（`/health` は除く）。
- クライアント IP は `CF-Connecting-IP` で受ける。CORS は `CORS_ORIGINS` / `allow_origin_regex`。
- タイムアウトの鎖: LLM 60 秒 < Cloud Run 90 秒 < Cloudflare 125 秒。
- h2c への切り替えを、アプリでやるか（切断の取り消しのため）。
- 未確認: Worker の Free プランの制限（90 秒より先）、Vercel Hobby の規約（公式の Hobby と Fair Use のページは 2026-10-24 に読み、個人・非商用ならよい。利用規約の本文は未読）、`@supabase/ssr` のクッキーの読み取り、125 秒の壁の挙動。

## やらないこと

- 新しいというだけで、Go・Django・gRPC・Celery・Redis・LiteLLM を入れない。入れるのは、製品の必要か、利用者が決めた学習の目的があるときだけ。
- 測定・要件・学習の目的のどれも無いまま、サービスを分けない。
- Supabase Auth と並べて、Django の認証を入れない。
- `chatbot` スキーマのマイグレーションの持ち主を二重にしない。
