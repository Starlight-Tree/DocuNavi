# 検索の評価（evals）

資料の検索（`app/agents/tools.py` の `search_chunks`、BM25）だけを、質問と正解の組で採点します。
資料群ごとの評価（`--corpus`・既定）と、アプリが実際に検索する全資料の評価（`--app`）があります。
**LLM も DB も呼びません**（無料で、毎回同じ結果になります）。検索を変える前後の差を数字で見るための道具です。

## 実行

```bash
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 5            # evals/results/baseline_bm25.json
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 2 --out evals/results/baseline_bm25_k2.json
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 5 --corpus evals/corpora/cafe   # PDF の資料
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 5 --corpus evals/corpora/guides # PDF の資料（取扱説明書・入寮規程）
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 5 --corpus evals/fixtures/menu # PDF の資料（メニュー・キャンペーン。アプリの外）
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 5 --app                       # アプリが検索する全資料（全部の質問）
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 2 --app --out evals/results/baseline_bm25_app_k2.json
```

| 引数 | 意味 |
|---|---|
| `--mode` | 検索の方式。今は `bm25` だけ（`scripts/eval_retrieval.py` の `MODES` に足す） |
| `--k` | 上位何ファイルまでを評価するか（既定 5） |
| `--corpus` | PDF の資料のディレクトリ。配下の PDF を、取り込みと同じ経路（`app/ingestion` の抽出とチャンク化）で読む。評価セットの既定は `<dir>/questions.yaml` |
| `--passages` | `--corpus` のときの表の返し方。`parent`（既定）は、表の行を 1 行ずつ採点し、採用されたら**表全体**を返す。`sentence` は、表も 1 行ずつの文として返す（比較用） |
| `--app` | アプリが検索する全資料（`storage/chunk/` の .txt と `storage/pdf/` の PDF）を、アプリと同じ検索（資料群ごとに採点して合わせる）で採点する。評価セットは `evals/questions.yaml` と `evals/corpora/*/questions.yaml` の全部（id は重ならないこと）。`SEARCH_SCOPE` には影響されず、全部を使う。`--corpus` とは同時に指定できない |
| `--allow-missing-evidence` | 根拠が抽出結果に無い質問があっても止まらず、`extraction_miss` として数えて測る（下の「失敗の種類」）。既定は、評価が黙って無効になるのを防ぐために、終了コード 2 で止まる。期待ファイルが資料に無いなどの誤りは、この指定があっても止まる |
| `--questions` | 評価セット（既定 `evals/questions.yaml`。`--corpus` なら `<dir>/questions.yaml`。`--app` なら全部の評価セット） |
| `--out` | 出力先（既定 `evals/results/baseline_<mode>.json`。`--corpus` 付きは `baseline_<mode>_<ディレクトリ名>.json`、`--app` は `baseline_<mode>_app.json`） |

評価セットが資料と合っていない（期待ファイルや根拠の文が無い）ときは、何も書かずに終了コード 2 で止まります。
`--corpus` では、取り込めない PDF（読めない・文字が無い・文字化け）があっても、黙って落とさず、名前と理由を出して止まります。
根拠の照合は、全角半角と空白（PDF の改行やセルの区切り）の違いを無視します。

## 質問の書式

先頭のコメントに項目の意味があります。`evals/questions.yaml`（ザーハード）のほかに、PDF の資料には次の項目も使えます。

| 項目 | 意味 |
|---|---|
| `evidence_mode` | `any`（既定）は、期待ファイルごとにどれか 1 つが返ればよい。`all` は、`evidence` の全部が返ること。表の集計・比較・絞り込みでは、一部の行だけでは答えを確定できないので `all` にする |
| `answer` | 正解の文。検索の評価では使わない（回答の評価のために持つ） |
| `page` | 根拠のページ（任意。空でよい）。書いてあれば、抽出結果と食い違うとき止まる。実際のページは、レポートの `evidence_pages` に、抽出結果から出る |
| `kind` | 細かい種別（`aggregate` `filter` `comparison` など）。集計は `category` のまま |

承認した質問の期待値は変えません。PDF 化や抽出でずれたときは、質問側を直さず、ずれを報告します。

## 指標

答えが資料にある質問（`factual` / `paraphrase` / `multi_hop`）について:

| 指標 | 意味 |
|---|---|
| `doc_recall_at_k` | 期待ファイルが上位 k 件に入った割合。`multi_hop` は期待ファイルが全部入ること |
| `keyword_hit_rate_at_k` | 期待ファイルごとに、そのファイルの検索結果の本文に `evidence` のどれか 1 つが含まれた割合。ファイル単位では測れない「答えの文が返ったか」を見る |
| `mrr` | 期待ファイルが最初に現れた順位の逆数の平均。入らなければ 0 |

資料に答えが無い質問（`out_of_scope`）について:

| 指標 | 意味 |
|---|---|
| `empty_answer_accuracy` | 何も返さなかった割合。`scope_kind` ごとの内訳も出す |

`scope_kind` は 2 種類です。`off_topic` は資料と無関係（天気など）、`on_topic_absent` はザーハードの話だが資料に書かれていない
（人口・首都など）。後者は、文章の中の語だけで一致する検索には本質的に難しく、**「空を返す」を期待値にするのが厳しすぎる**可能性があります。
LLM が「資料に無い」と答えられるかは、この評価では測れません（回答の評価は別の段階）。

## 失敗の種類（`failure_category`）

| 種類 | 意味 |
|---|---|
| `no_hit` | 何も返らなかった |
| `wrong_file` | 何か返ったが、期待ファイルが（全部は）入っていない |
| `wrong_rank` | 期待ファイルは返ったが、先頭ではない |
| `keyword_miss` | 期待ファイルは先頭だが、根拠の文が返っていない |
| `paraphrase_miss` | `paraphrase` の質問での `no_hit` / `wrong_file` / `keyword_miss`（言い換えが原因かを見るため、まとめている） |
| `unexpected_result` | `out_of_scope` なのに何か返った |
| `extraction_miss` | 根拠の文が、PDF の抽出結果に無い。検索の失敗ではなく、読み取り（抽出・チャンク化）の失敗。`--allow-missing-evidence` のときだけ付き、上のどれよりも優先する |

`extraction_miss` は、質問の根拠が PDF の見た目から書かれている（抽出結果から書いていない）から検出できます。
`summary.extraction_miss` に、件数・質問の id と、**読み取れた質問だけの指標**（`extracted_only`）を出します。全体の指標
（`doc_recall` など）は、読み取りの失敗も含むパイプライン全体の結果で、検索だけの良し悪しは `extracted_only` で見ます。
`extraction_miss` が多い PDF は、検索の改善では直らない（チャンク化・抽出の問題として扱う）。

## baseline の見方

2026-10-15 時点の実測（資料 3 ファイル、質問 36 件。回答可能 24、資料に無い 12）:

| | k=5 | k=2 |
|---|---|---|
| doc_recall | 21/24 | 20/24 |
| keyword_hit | 21/24 | 20/24 |
| mrr | 0.8958 | 0.8958 |
| empty_answer（off_topic） | 8/8 | 8/8 |
| empty_answer（on_topic_absent） | 0/4 | 0/4 |

- **factual 16/16、paraphrase 3/5、multi_hop 2/3（k=5）。** 資料の言葉で聞けば拾え、資料に無い語での言い換えは拾えません。
- **失敗 8 件の内訳（k=5）。** `paraphrase_miss` 2（気温差・毒ガス。資料は「温度差」「有害なガス」）、`wrong_rank` 1、
  `wrong_file` 1（`q030`。2 つ目のファイルが返らない）、`unexpected_result` 4（`on_topic_absent` の全部）。
- **見る順番。** (1) 失敗した質問の `retrieved`（何が返ったか）を読む。(2) `failure_category` で偏りを見る。
  (3) 偏りが「言い換え」なら、語の一致では原理的に拾えないので、意味で拾う手段（同義語、埋め込み）の候補になる。
  偏りが「資料に無いのに返る」なら、空を返す条件（スコアのしきい値）の問題で、検索方式を変えても残る。

## guides の PDF の baseline（段階 2、2026-10-15）

含まない。検索の評価では問題にならず、回答の評価で扱う（まだ決めていない）。

| keyword_hit | 9/14（0.6429） |

失敗 7 件（k=5。t004 を直す前は 8 件で、t004 も含んでいた）の分類。原因は見立てで、検索の定数は結果に合わせて直していない:

資料の言葉で聞いても落ちるので、ベクトル検索の前に、`MIN_SHARED_TERMS` の扱いを決める価値がある。(2) 言い換え（a004・t005）は

(b) LLM が検索クエリを書き換えて落ちる（t001）ので、クエリにユーザーの語をそのまま含めるよう、システムプロンプトかツールの返答で促す。実 API で測る必要がある。

## ベクトル検索の比較（BM25・ベクトル・ハイブリッド、2026-10-18。測っただけ。アプリのコードは変えていない）

Supabase に入れた 68 チャンクの埋め込み（`gemini-embedding-2`、768 次元）が、検索に役立つかを測った。**同じ 68 チャンク・同じ 32 問**（cafe 10 + guides 22）で、
3 方式を比べる。アプリの検索経路は切り替えていない。資料も足していない。

**手順と道具。** `scripts/eval_vector.py`（DB は読み取り専用の接続で、`chatbot_app` が読むだけ。API を呼ぶのは質問の埋め込みだけで、LLM は呼ばない）:

```bash
python -m scripts.eval_vector plan                    # 分割と正解チャンクを確定 -> evals/vector/plan.json（検索の結果を見る前に作る）
python -m scripts.eval_vector embed-queries           # 送る件数・概算費用を表示するだけ（--apply で実 API。evals/cache/ に保存。Git 管理外）
python -m scripts.eval_vector dev                     # 調整用の質問だけで測り、しきい値を決める -> results/vector_dev.json
python -m scripts.eval_vector final                   # 固定したまま held-out を 1 回だけ -> results/vector_final.json（既にあれば上書きしない）
```

- **分割。** 層（期待ファイル 3 つ、資料外）ごとに、`sha256("vector-eval-v1:" + id)` の順で先頭の `round(n × 0.4)` 件を held-out にした。dev 19 問（答えあり 13・資料外 6）、
  held-out 13 問（答えあり 9・資料外 4）。held-out は、方式・しきい値の調整に使っていない（`final` は `vector_dev.json` のしきい値をそのまま読む）。
- **正解チャンク。** DB のチャンク本文（見出しを含む）に、質問の根拠が正規化後に含まれるチャンク。答えのある 22 問すべてで、根拠ごとにちょうど 1 チャンク
  （`evals/vector/plan.json`）。採点の意味は既存の `keyword_hit` と同じ（any: 期待ファイルごとに根拠のどれか / all: 根拠の全部）を、チャンク単位にしたもの。
- **3 方式。** BM25 = アプリの採点（`tools.search_collections`）を、順位をつける単位だけファイルからチャンクに変えたもの（採点する文の集合は同じ。DB のチャンクが
  PDF からの作り直しと一致することも確かめる）。ベクトル = pgvector のコサイン（`OPERATOR(extensions.<=>)`）。ハイブリッド = 上位 20 件ずつの
  Reciprocal Rank Fusion（定数 60。調整していない）。
- **答えなしの規則（先に固定）。** BM25 は、何も当たらなければ空。ベクトルは、1 位の類似度がしきい値未満。ハイブリッドは、BM25 が空かつ類似度がしきい値未満。
  しきい値は dev だけで、「答えのある質問を残した率」と「資料外を断れた率」の平均が最大のもの（同点は小さい方）。決まった値: ベクトル 0.728959、ハイブリッド 0.713484。

**結果（チャンク単位。hit@k = 上位 k チャンクで根拠がそろった問数）。**

| 方式 | 分割 | MRR | hit@1 | hit@3 | hit@5 | 答えありを断った | 資料外を断れた |
|---|---|---|---|---|---|---|---|
| BM25 | dev（13 / 6） | 0.673 | 8 | 9 | 10 | 1 | 3 |
| ベクトル | dev | 0.923 | 11 | 13 | 13 | 1 | 5 |
| ハイブリッド | dev | 0.846 | 9 | 13 | 13 | 1 | 3 |
| BM25 | held-out（9 / 4） | 0.722 | 6 | 7 | 7 | 2 | 3 |
| ベクトル | held-out | 0.944 | 8 | 9 | 9 | 1 | 4 |
| ハイブリッド | held-out | 0.944 | 8 | 9 | 9 | 0 | 3 |

2 つを合わせると（答えあり 22・資料外 10）: hit@1 は BM25 14・ベクトル 19・ハイブリッド 17。hit@3 は 16・22・22。答えありを断った数は 3・2・1（BM25: t005・a005・t003、ベクトル: t005・t001、
ハイブリッド: t005）。資料外を断れた数は 6・9・6。
BM25 が返す本文（採点した文とその前後）に根拠があるかで数えると、hit@1/3/5 は dev で 7/8/9、held-out で 6/7/7（チャンクの一致より厳しい）。

- **BM25 が落とした言い換えの質問を、ベクトルは拾った。** BM25 が上位 20 件にも根拠のチャンクを出せなかったのは c004・a004・t005・a005・t003。ベクトルは、このうち 5 問すべてで 2 位以内に出した。
  逆にベクトルが BM25 に負けたのは c006（1 位 → 2 位）の 1 問だけ。
- **資料外の断りは、ベクトルのしきい値が 1 問ずつの差で決まっている。** 1 位の類似度は、答えのある質問が 0.68〜0.89、資料外が 0.57〜0.77 で重なる。
  dev で決めた 0.729 は、答えのある t005（0.682）を断り、held-out でも答えのある t001（0.698）を断った。資料外の a009（0.712）・t008（0.714）は、このしきい値の少し下にいて断れている。
  **別のしきい値や別の質問では動く。** ハイブリッドのしきい値は、dev の曲線が 0.713 以上でほぼ平らで、実質は「BM25 が空のとき」とほぼ同じ。
- **遅延と費用（中央値）。** BM25 の検索 2〜5 ms、ベクトルの DB 問い合わせ約 24 ms（接続は検索ごとではなく、評価の間つないだまま）。質問の埋め込みは、8 件を 1 回で送って 1.1〜1.4 秒
  （1 件ずつ送ったときの遅延は測っていない）。アプリで使うと、質問のたびに埋め込みの API を 1 回呼ぶ追加が要る。今回の送信は 32 件・4 回・失敗 0、約 1,800 文字
  （概算 $0.0004。実際の請求は未確認）。

**限界（結果を読むときに）。**
- **件数が少ない。** 答えあり 22 問・資料外 10 問、held-out は 9 問と 4 問。1 問で数字が動く。信頼区間は出していない。
- **held-out は独立ではない。** 32 問は BM25 の調整・測定で何度も見ていた質問で、BM25 の規則はこの質問に合わせて決めた。ベクトルとハイブリッドはこの質問で調整していない
  （しきい値だけ dev で決めた）ので、BM25 に有利な偏りはあっても、ベクトルに有利な偏りは小さいはず。ただし、方式の最終判断には、これまで見ていない質問が要る。
- **tsubasa は 3 チャンクしかない。** t 系の 7 問は、k=3 以上なら全チャンクが返るので、hit@3 と hit@5 は自明に近い（hit@1 と MRR は意味がある）。
- **質問文をそのまま検索に渡している。** 実際の LLM は、質問を言い換えたクエリで検索する（回答の評価の t001）。この影響は測っていない。
- **回答の質は測っていない。** 検索が良くなったことと、回答が良くなったことは別。資料群は 2 つ（68 チャンク）で、資料が増えたときの挙動も未確認。
- **再現。** 質問の埋め込みは `evals/cache/`（Git 管理外）にあり、消すと 32 件を取り直す（API の埋め込みは同じ入力でも僅かに揺れうる）。`plan.json` と結果は DB のチャンクの指紋
  （`corpus_fingerprint`）を持ち、DB が変わると `dev` / `final` は止まる。コードは `git_head` の時点のもの（結果ファイルに記録。未コミットの変更があれば、その分は含まない）。
