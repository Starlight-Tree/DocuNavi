# 検索の評価（evals）

資料の検索（`app/agents/tools.py` の `search_chunks`、BM25）だけを、質問と正解の組で採点します。
資料群ごとの評価（`--corpus`・既定）と、アプリが実際に検索する全資料の評価（`--app`）があります。
**LLM も DB も呼びません**（無料で、毎回同じ結果になります）。検索を変える前後の差を数字で見るための道具です。

## 実行

```bash
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 5            # evals/results/baseline_bm25.json
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 2 --out evals/results/baseline_bm25_k2.json
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 5 --corpus evals/corpora/cafe   # PDF の資料
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 5 --app                       # アプリが検索する全資料（全部の質問）
.venv/bin/python -m scripts.eval_retrieval --mode bm25 --k 2 --app --out evals/results/baseline_bm25_app_k2.json
```

| 引数 | 意味 |
|---|---|
| `--mode` | 検索の方式。今は `bm25` だけ（`scripts/eval_retrieval.py` の `MODES` に足す） |
| `--k` | 上位何ファイルまでを評価するか（既定 5） |
| `--corpus` | PDF の資料のディレクトリ。配下の PDF を、取り込みと同じ経路（`app/ingestion` の抽出とチャンク化）で読む。評価セットの既定は `<dir>/questions.yaml` |
| `--passages` | `--corpus` のときの表の返し方。`parent`（既定）は、表の行を 1 行ずつ採点し、採用されたら**表全体**を返す。`sentence` は、表も 1 行ずつの文として返す（比較用） |
| `--app` | アプリが検索する全資料（`storage/chunk/` の .txt と `storage/pdf/` の PDF）を、アプリと同じ検索（資料群ごとに採点して合わせる）で採点する。評価セットは `evals/questions.yaml` と `evals/corpora/*/questions.yaml` の全部（id は重ならないこと）。`SEARCH_SCOPE` には影響されず、全部を使う。`--corpus` とは同時に指定できない |
| `--questions` | 評価セット（既定 `evals/questions.yaml`。`--corpus` なら `<dir>/questions.yaml`。`--app` なら全部の評価セット） |
| `--out` | 出力先（既定 `evals/results/baseline_<mode>.json`。`--corpus` 付きは `baseline_<mode>_<ディレクトリ名>.json`、`--app` は `baseline_<mode>_app.json`） |

評価セットが資料と合っていない（期待ファイルや根拠の文が無い）ときは、何も書かずに終了コード 2 で止まります。
`--corpus` では、取り込めない PDF（読めない・文字が無い・文字化け）があっても、黙って落とさず、名前と理由を出して止まります。
根拠の照合は、全角半角と空白（PDF の改行やセルの区切り）の違いを無視します。

## ファイル

| パス | 内容 |
|---|---|
| `questions.yaml` | 質問と正解。項目の意味はファイル先頭のコメント |
| `results/baseline_bm25.json` | 現行 BM25 の実測（k=5）。質問ごとの返した本文と失敗の種類を含む |
| `results/baseline_bm25_k2.json` | 同じ評価を k=2 で。**アプリが LLM に渡す件数（`TOP_K`）はこちら** |
| `results/baseline_bm25_app.json` / `_app_k2.json` | アプリが検索する全資料（ザーハード + カフェ）を、全部の質問（46 件）で採点した実測。k=5 / k=2 |
| `corpora/cafe/` | 別の評価用の資料（架空のカフェチェーンの店舗案内。表・脚注・例外つき）。`source/` は PDF 化する前の Markdown と事実リスト、`questions.yaml` は承認済みの質問（作成者・承認者・基準は先頭に記録）、`cafe_store_guide.pdf` は `source/make_pdf.py`（reportlab + IPAex ゴシック。依存は一時的な環境にだけ入れる）で Markdown から作った 4 ページの PDF（表は 3〜4 ページにまたがる。同じ入力から同じバイト列）。同じファイルを `storage/pdf/cafe/` にも置いていて、アプリはそちらを検索する（一致はテストが確かめる） |
| `../scripts/eval_retrieval.py` | 採点の本体 |
| `../tests/test_eval_retrieval.py` | 採点の道具のテストと、baseline からの退行の検知 |

## 質問の書式

先頭のコメントに項目の意味があります。`evals/questions.yaml`（ザーハード）のほかに、PDF の資料には次の項目も使えます。

| 項目 | 意味 |
|---|---|
| `evidence_mode` | `any`（既定）は、期待ファイルごとにどれか 1 つが返ればよい。`all` は、`evidence` の全部が返ること。表の集計・比較・絞り込みでは、一部の行だけでは答えを確定できないので `all` にする |
| `answer` | 正解の文。検索の評価では使わない（回答の評価のために持つ） |
| `page` | 根拠のページ（任意。空でよい）。書いてあれば、抽出結果と食い違うとき止まる。実際のページは、レポートの `evidence_pages` に、抽出結果から出る |
| `kind` | 細かい種別（`aggregate` `filter` `comparison` など）。集計は `category` のまま |

承認した質問の期待値は変えません。PDF 化や抽出でずれたときは、質問側を直さず、ずれを報告します。

## 指標

答えが資料にある質問（`factual` / `paraphrase` / `multi_hop`）について:

| 指標 | 意味 |
|---|---|
| `doc_recall_at_k` | 期待ファイルが上位 k 件に入った割合。`multi_hop` は期待ファイルが全部入ること |
| `keyword_hit_rate_at_k` | 期待ファイルごとに、そのファイルの検索結果の本文に `evidence` のどれか 1 つが含まれた割合。ファイル単位では測れない「答えの文が返ったか」を見る |
| `mrr` | 期待ファイルが最初に現れた順位の逆数の平均。入らなければ 0 |

資料に答えが無い質問（`out_of_scope`）について:

| 指標 | 意味 |
|---|---|
| `empty_answer_accuracy` | 何も返さなかった割合。`scope_kind` ごとの内訳も出す |

`scope_kind` は 2 種類です。`off_topic` は資料と無関係（天気など）、`on_topic_absent` はザーハードの話だが資料に書かれていない
（人口・首都など）。後者は、文章の中の語だけで一致する検索には本質的に難しく、**「空を返す」を期待値にするのが厳しすぎる**可能性があります。
LLM が「資料に無い」と答えられるかは、この評価では測れません（回答の評価は別の段階）。

## 失敗の種類（`failure_category`）

| 種類 | 意味 |
|---|---|
| `no_hit` | 何も返らなかった |
| `wrong_file` | 何か返ったが、期待ファイルが（全部は）入っていない |
| `wrong_rank` | 期待ファイルは返ったが、先頭ではない |
| `keyword_miss` | 期待ファイルは先頭だが、根拠の文が返っていない |
| `paraphrase_miss` | `paraphrase` の質問での `no_hit` / `wrong_file` / `keyword_miss`（言い換えが原因かを見るため、まとめている） |
| `unexpected_result` | `out_of_scope` なのに何か返った |

## baseline の見方

2026-10-15 時点の実測（資料 3 ファイル、質問 36 件。回答可能 24、資料に無い 12）:

| | k=5 | k=2 |
|---|---|---|
| doc_recall | 21/24 | 20/24 |
| keyword_hit | 21/24 | 20/24 |
| mrr | 0.8958 | 0.8958 |
| empty_answer（off_topic） | 8/8 | 8/8 |
| empty_answer（on_topic_absent） | 0/4 | 0/4 |

- **factual 16/16、paraphrase 3/5、multi_hop 2/3（k=5）。** 資料の言葉で聞けば拾え、資料に無い語での言い換えは拾えません。
- **失敗 8 件の内訳（k=5）。** `paraphrase_miss` 2（気温差・毒ガス。資料は「温度差」「有害なガス」）、`wrong_rank` 1、
  `wrong_file` 1（`q030`。2 つ目のファイルが返らない）、`unexpected_result` 4（`on_topic_absent` の全部）。
- **見る順番。** (1) 失敗した質問の `retrieved`（何が返ったか）を読む。(2) `failure_category` で偏りを見る。
  (3) 偏りが「言い換え」なら、語の一致では原理的に拾えないので、意味で拾う手段（同義語、埋め込み）の候補になる。
  偏りが「資料に無いのに返る」なら、空を返す条件（スコアのしきい値）の問題で、検索方式を変えても残る。

## カフェの PDF の baseline（2026-10-15）

`--corpus evals/corpora/cafe`。PDF 1 冊・4 ページ・30 チャンク（表は 1 チャンク、3〜4 ページ）、質問 10 件（回答可能 8、資料に無い 2）。

| | k=5 | k=2 |
|---|---|---|
| doc_recall | 8/8 | 8/8 |
| keyword_hit | 6/8 | 6/8 |
| mrr | 1.0 | 1.0 |
| 空返しの正解（off_topic / on_topic_absent） | 1/1 / 0/1 | 1/1 / 0/1 |

抽出の確認（`--corpus` の事前検査）は通っている: 31 件の根拠はすべて抽出結果にあり、集計の質問の根拠は表の 12 行（3 ページと 4 ページ）にまたがって見つかる。

失敗 3 件の読み方（原因は未調整。質問も検索の定数も、結果に合わせて直していない）:

| 質問 | 種類 | 原因の見立て |
|---|---|---|
| c001 創業はいつ | keyword_miss | 答えの文は「みなとコーヒー」を含まず、質問と共有する 2-gram が「創業」の 1 つだけ。共有 2 つ以上という条件（`MIN_SHARED_TERMS`）で、候補から落ちる |
| c004 スマホで注文できない店舗 | paraphrase_miss | 資料は「モバイルオーダー」「利用できません」。語が一致しない言い換え（意味で拾う手段が要る種類。ただし、明確な言い換え失敗はこの 1 件だけ） |
| c010 みなとブレンドの価格 | unexpected_result | 資料に価格は無いが、「みなとブレンド」を含む文が返る（資料に無い質問への空返し。`on_topic_absent`） |

**表の返し方で、同じ質問・同じ検索の定数が、どう変わったか**（表の質問は c006 最多・c007 絞り込み・c008 比較の 3 件）:

| 返し方 | 表の質問 | keyword_hit |
|---|---|---|
| 表を行ごとの文として返す（`--passages sentence`。チャンク化の第 1 版と同じ） | c008 だけ通る | 4/8 |
| 表全体を 1 つの文として採点する（実験。コミットしていない） | c006 だけ通る（長い 1 文が BM25 の長さの補正で不利になり、他の短い文に負ける） | 4/8 |
| 行ごとに採点し、採用されたら表全体を返す（`--passages parent`。**既定**） | 3 件とも通る | 6/8 |

表の問題は、チャンク化ではなく検索の返し方（採点の単位と返す単位が同じだったこと）だった。表のチャンクは、全体が `HARD_LIMIT_CHARS` に
収まればページをまたいでも 1 つ、収まらないときだけ行の範囲で分けて見出し行を繰り返す。

## アプリ全体の baseline（2026-10-15）

`--app`（k=5 / k=2）。ザーハード 36 件 + カフェ 10 件 = 46 件、資料群は `zahard`（.txt 3 件）と `cafe`（PDF 1 件）。

| 指標 | k=5 | k=2 |
|---|---|---|
| doc_recall | 29/32（0.9062） | 28/32（0.875） |
| keyword_hit_rate | 27/32（0.8438） | 26/32（0.8125） |
| mrr | 0.9219 | 0.9219 |
| empty_answer_accuracy | 9/14（off_topic 9/9、on_topic_absent 0/5） | 同じ |

- **資料群を足しても、既存の結果は動かない。** 質問ごとに返るファイルの並びが、各資料群を単独で評価したときと同じで、
  失敗の内訳は単独の 2 つの和（k=5: 11 件）に一致する。`tests/test_eval_retrieval.py` が、この一致を見張る。
- **1 つに混ぜると崩れる（実測。コードには残していない）。** ザーハードの 40 文とカフェの 94 文を 1 つの資料として採点すると、
  「ザーハード」の 2-gram の出現率が 0.475 から 0.142 に下がり、主題語の除外（`GENERIC_TERM_RATIO` = 0.25）が効かなくなる。
  ザーハードの 8 問で、返るファイルが増えた（q001 は 1 件から 3 件）。該当数の指標は 21 から 22 に「上がる」が、
  無関係な文が増えただけで、採点には出ない。**指標が良くなっても、返る件数を見ないと気づけない。**
- **どちらの資料群にも当たる質問は、まだ無い。** 評価セットの質問は、別々に検索すると、どちらか片方の資料群にしか当たらない
  （ザーハードの 36 問はカフェに 0 件、カフェの 10 問はザーハードに 0 件）。両方に当たる質問での合わせ方（順位の交互採用）は、
  実際の質問では確かめていない。
- **`on_topic_absent` は 0/5。** 話題は合っているが、答えの事実が資料に無い質問に、空を返せていない。混ぜる前からの課題
  （単独の評価でも 0/4、0/1）。

## 限界

- **PDF の資料は、機械が組んだ PDF 1 冊（カフェの店舗案内）だけ。** Word や Google Docs の書き出し、2 段組み、画像だけのスキャン PDF は、
  まだ試していない。チャンク化（`app/ingestion/chunker.py`）は、座標から行・段落・見出し（文字が大きい行）・表（セルの間が空いた行の並び）を
  組み直す。太字だけで大きさが同じ見出しや、2 段組みは、扱いが弱い。
- **表の返し方は、表が 1 つの質問に答えるときだけ確かめた。** 表のまとまりは、行のどれかが採用されれば全体を返す。長い表（収まらずに
  行の範囲で分けた表）や、表が複数あって別々の表の行が要る質問は、まだ確かめていない。

- **件数が少ない。** 回答可能 24 件なので、1 件の増減が約 4 ポイント。割合ではなく件数で比べる。
- **資料が 3 ファイルしかない。** `k` が 3 以上なら結果は同じ（`k=3` と `k=5` は同一）。ファイル単位の指標は甘く出る。
  資料が増えてから意味が出る。
- **質問は資料を読んで書いた。** 実際の利用者の質問ではない。実装に合わせ込まないように、q030 以降は検索の結果を見る前に書いた。
  質問や期待値を結果に合わせて直さない（直すなら、理由をコミットに書く）。
- **`keyword_hit` は部分文字列の有無。** 返った文が答えとして正しいか、LLM が正しく答えるかは測らない。
- **回答の質（根拠への忠実さ、拒否の仕方）は測らない。** LLM を呼ぶ別の評価になる。

## 更新のしかた

- 質問を足す、または検索を変えたら、上の 2 コマンドで baseline を取り直し、数字が変わったときだけコミットする
  （`generated_at` だけが変わる差分は、コミットしない）。
- `tests/test_eval_retrieval.py` は、現在の検索が baseline より該当数を減らしたら失敗する（CI の `backend` ジョブで動く）。
  資料が変わったときは skip になるので、baseline を取り直す。アプリ全体の baseline（`_app`）は、件数ではなく質問ごとの
  返るファイルの並びまで一致を求める（動いたら、良くも悪くも知らせる）。
- 資料群を足す・PDF を差し替えたら、`--app` の 2 コマンドも取り直す（資料の sha256 が変わると、アプリ全体の退行の検知は skip になる）。
- 質問の元は `tests/rag_eval_cases.py` と同じもの（q001-q029）を含む。両方を変えるときは同期テストが落ちる。

## 次に見るもの

1. **PDF を増やしたあと**（段階 2）: 同じコマンドで取り直し、`corpus.sha256` と `search_params` を突き合わせる。
   `GENERIC_TERM_RATIO` と `MIN_SHARED_TERMS` は資料群ごとの統計に使う値で、資料群の中のファイルが増えたときの挙動を記録する。
   別の資料群に足す PDF は、その資料群の質問を評価セットに足し、`--app` で他の資料群が動かないことを確かめる。
2. **`on_topic_absent` の扱い**: 検索で空を返すのか、LLM に「資料に無い」と答えさせるのかを決める。決めてから、ベクトル検索の
   類似度のしきい値を評価する（ベクトル検索は常に近傍を返すので、しきい値が無いと全部 `unexpected_result` になる）。
3. **`wrong_file`（q030）**: 2 つ目のファイルが返らない原因（件数の絞り込み `RELATIVE_SCORE_CUTOFF`、文の選び方）は未調査。
