# 評価（evals/）を触るとき

詳細は [evals/CLAUDE.md](../../evals/CLAUDE.md) と [evals/README.md](../../evals/README.md)。

- `corpora/` はアプリの検索対象（`storage/pdf/` に同じ PDF がある）。`fixtures/` は対象外で、`storage/pdf/` にも本番 DB にも入れない
- 質問の ID は評価セットをまたいで重ねない（`--app` が止まる）。新しい接頭辞は `evals/CLAUDE.md` の表に足す。`x` 始まりは使わない
- 承認済みの質問の期待値は変えない。PDF や抽出でずれたら、質問を直さず報告する
- `results/` の既存ファイルを上書きしない（`--out` で別名にする）。`cache/` はコミットしない
- 実 API（埋め込み・LLM）は、質問文・回数・概算費用を示して承認を得てから。キーは環境変数だけから読み、`.env` は開かない

## 実 API で条件を比べる評価（プロンプト・モデルなど）

2026-11-16 の Promptfoo の段階 A で、フォールバックの設定により遅い回だけ別モデルが答えた（3 回）。測り始めてから気づいた反省。

- 測る前に条件を固定し、差分を示す: 主モデル、フォールバック（無効にする。`evals/promptfoo/provider.py` が `GEMINI_FALLBACK_MODEL` を空にする）、ヘッジ（比較用は無効にするのが望ましいが、provider は本番と同じ有効のまま）、認証・API 経路、各層（Promptfoo・アプリ・SDK）の再試行。固定していない項目は、固定していないと書く
- 本番規模の前に、同時実行 1 の少数（追質問を含む 2〜3 会話）で予備実行し、採用モデル・実呼び出し数・429・タイムアウト・終了後に処理が残らないかを確かめる
- 回数は分けて報告する: 実行済み、やり直しの予定、ヘッジ・再試行を含む総呼び出しの上限、課金経路と費用の上限。「費用は変わらない」と言い切らない
- 会話テストは、あるターンの回答が次のターンの履歴に影響する。混入が分かったら、混入したターンだけでなく会話単位で除く（遅いケースだけ除くと、速いケースに偏る）
- 混入した実行は診断用に残す。正式な比較は、条件を直した新しい実行 ID で行う。全件の再実行と本番の変更は、別に承認を得る
- ターンごとの採用モデルと追加呼び出しは、まだ記録できない（時間の一致による推定だけ）。記録できる形にするのは未対応
