# UI レビューの制約

- 「見た目が微妙」だけでは指摘しない。必ず、影響・根拠・修正案を添える
- 実装の前に、「見た目をどこまで変えるか」（最小 / 中程度 / 大胆）を確かめる。指定が無いまま、機能だけの変更に寄せない
- 画面のレイアウトを変える変更（サイドバー・ヘッダー・画面構成の追加や変更など）は、実装の前に、Claude Design でモックを作る（Artifact の Design 型。使えないときは、実データの HTML モックを Artifact で）。モックは 2 案以上を示し、利用者に選んでもらう
- モックを省く場合は、省くことと理由を実装の前に伝え、承認を得てから進める。「機能追加だから省略」という判断を、承認なしにしない（2026-10-19、会話一覧のサイドバーで、モックを作らず伝えずに実装した）
- モバイル専用の最適化（カード化・タッチ配慮・矢印など）を、指示なく行わない（スマホ実機は想定しない）
- 競合比較で、実機で確認していない製品を「実測」として扱わない。公式の文書は B、第三者の記事・レビューは C と書く
- 「リサーチして」「他社と比べて」「どっちがいいか」と頼まれたら、`.claude/skills/ux-review/SKILL.md` の「5. モックの比較リサーチ」の手順で進める。始める前に `docs/ux-research.md` と記憶で過去の結果を確かめ、終わったら `docs/ux-research.md` に結果（出典・等級・見なかったもの）を残す（2026-10-26、前回の調査結果が残っておらず、やり方を聞かれても答えられなかった）
- 競合の画面を画像で見ていないときは、「画像は見ていない」と書く。文字の説明だけで画面の優劣を言わない
- レビューや比較は、「画面をどう変えるか」まで落とす。ただし、実装に進むのは、依頼に実装が含まれるとき、または確認が取れたときだけ
- 基準はデスクトップブラウザ（幅 1280px 前後）。スマホ実機での利用は想定しない。390px は「レイアウトが壊れないか」の確認だけで、モバイル向けの最適化はしない
- 画面を変えたら、Before / After の Playwright スクリーンショットを撮る（保存先は `.playwright-mcp/`）
- 「見た目を変える」依頼は、色・余白・書体・密度の変更を含める。機能だけの変更では、見た目の差が出ない
- 競合など他社の比較の証拠等級は、A: 実機で確認 / B: 公式の文書 / C: 第三者の記事 / 不明。実機で確認していないことを「確認済み」と書かない
