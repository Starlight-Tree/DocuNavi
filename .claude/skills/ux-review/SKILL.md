# UX レビューの進め方

## 前提

- デスクトップブラウザ（幅 1280px 前後）が基準。スマホ実機は想定しない。390px は「壊れないか」の確認だけ
- 実装の前に、「見た目をどこまで変えるか」（最小 / 中程度 / 大胆）を確かめる
- 実 API の呼び出し（課金）は、始める前に確認する。回答の画面は、ブラウザー内で応答を置き換えて撮れる（Playwright の `page.route` で `/chat/stream` を差し替える）

## レビューの種類

1. UX レビュー（導線・情報設計・タスクの完結性）
2. 見た目のレビュー（色・余白・書体・密度・部品の形）
3. 競合比較（公開情報ベース）
4. 再デザイン案

## 手順

### 1. UX レビュー
- 想定ユーザーと目的を挙げる
- 代表タスクを 8〜15 個挙げ、現状を評価する（成立するか、操作の数、迷い、行き止まり）
- あるべき体験を、タスクごとに決める
- 差を、優先順位（High / Medium / Low）つきで整理する

### 2. 見た目のレビュー
- 実画面（Playwright）を、1280px のライト・ダークで撮る。390px は崩れの確認だけ
- 色・余白・書体・密度・部品の形を評価する
- Before / After の画像で、差を示す

### 3. 競合比較
- 他社の製品は操作しない。公式の文書・公式ブログ・レビュー・解説記事を情報源にする
- 証拠等級を必ず付ける（A: 実機で確認 / B: 公式の文書 / C: 第三者の記事 / 不明）。A はドキュナビだけ
- 画面と導線の「型」を、観点ごとに比べる。製品全体の優劣の順位は出さない
- 読めなかったページは「読めなかった」と書く

### 4. 再デザイン案
- 3 案（最小 / 中程度 / 大胆）を、実データのモックで示す
- 各案に、Before / After の差と、実装の費用を書く
- おすすめを 1 つ選び、理由を述べる。API の変更が要る部分は、分けて書く

## 出力

- 総評（3 行以内）
- 問題点（影響・根拠・修正案・工数の目安）
- Before / After の画像
- 優先順位つきの改善リスト
- 参考資料（URL・種類・等級）

## しないこと

- 「見た目が微妙」だけで指摘しない
- 実機で確認していないことを「確認済み」と書かない
- 頼まれていない実装・リファクタを始めない（提案まで）
